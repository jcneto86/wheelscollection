# Wheels Collection — Web version (HTML + Tailwind + Alpine + Firebase)

**English** · [Português (Brasil)](README.pt-BR.md)

A **static SPA** for organizing a collection of Hot Wheels cars.
This is the version that replaces the Flutter app: it does not need compilation,
does not use Flutter Web, and runs on any shared hosting, including Hostinger,
inside `public_html/app`.

- **Front-end:** HTML5, Tailwind CSS (CDN) and Alpine.js 3.14.9 (ESM).
- **Back-end as a Service:** Firebase Auth (email/password) and Cloud Firestore.
- **Images:** square crop in the browser with Canvas, exported at
  **500 × 500 px** and saved as **Base64 inside the Firestore document**.
- **Languages:** `en-CA`, `fr-CA` and `pt-BR`, switched instantly without reloading.
- **Preferences:** theme, color palette and language in `localStorage`.
- **Routes:** hash-based (`#/...`), so they work in any subfolder without
  `mod_rewrite`.

An unauthenticated user who tries to open a protected route is sent to
`#/login`; after logging in they return to the intended route. An authenticated
user who opens `#/login` is sent to the dashboard.

## 2. Data model

Firestore collection:

```text
hotwheels_items/{itemId}
```

| Field | Type | Rule |
| --- | --- | --- |
| `userId` | `string` | Equal to the Firebase Auth UID; effectively immutable |
| `name` | `string` | 1 to 120 characters |
| `description` | `string` | 1 to 2000 characters |
| `imageBase64` | `string` | JPEG without the `data:` prefix; up to 900,000 characters |
| `createdAt` | `timestamp` | `serverTimestamp()` on creation |
| `updatedAt` | `timestamp` | `serverTimestamp()` on creation and edit |

The rules in `firestore.rules`:

- only allow read/write when `request.auth != null`;
- require `userId == request.auth.uid`;
- validate all fields, sizes and types;
- prevent changing `createdAt` on an edit;
- prevent reading or changing documents from another account.

The app query is just
`where('userId', '==', uid)`. Since there is **a single equality filter**, no
composite index is needed (`firestore.indexes.json` stays empty). Sorting by
date is done on the client.

> The old Flutter app collection was `cars`, with the `ownerId` field. Old data
> **does not appear automatically** in this version. See section
> [Migrate old data](#13-migrate-old-data-optional).

## 3. Configure Firebase

### 3.1 Create the project and the Web app

1. Open <https://console.firebase.google.com/> and create a project (or use an
   existing one).
2. Under **Project overview → Project settings → General**, scroll to
   **Your apps** and click the **Web** icon (`</>`).
3. Give it a nickname (e.g. `wheelscollection-web`) and register the app.
   Firebase Hosting does not need to be configured.
4. Copy the displayed `firebaseConfig` object.

The `js/firebase-config.js` file already comes filled in with the existing
`wheelscollection-ee9af` project. If you use another project, replace the
values:

```js
export const firebaseConfig = Object.freeze({
  apiKey: '...',
  authDomain: 'YOUR_PROJECT.firebaseapp.com',
  projectId: 'YOUR_PROJECT',
  messagingSenderId: '...',
  appId: '1:...:web:...',
  measurementId: 'G-...', // optional; the app does not initialize Analytics
});
```

Required fields checked by the app: `apiKey`, `authDomain`, `projectId`
and `appId`. If any is empty or contains placeholder text (`YOUR_...`), the app
shows a setup screen instead of breaking.

> The Firebase `apiKey` is **public per project**. It identifies the project,
> it does not authorize data access. Real protection comes from the Security
> Rules and the authorized domains.

### 3.2 Enable email/password authentication

1. In the Console: **Build → Authentication → Get started**.
2. **Sign-in method → Email/password** → enable **Email/password** and save.
3. Under **Authentication → Settings → Authorized domains**, check:
   - `localhost` (included by default, for development);
   - `YOUR_PROJECT.firebaseapp.com` (default);
   - **the Hostinger domain**, for example `yourdomain.com`,
     `www.yourdomain.com` and/or `app.yourdomain.com`.
4. Optional: under **Templates**, customize the sender and the text of the
   password reset email.

Without the correct domain under **Authorized domains**, login works locally
but fails in production with `auth/unauthorized-domain`.

### 3.3 Create Cloud Firestore

1. In the Console: **Build → Firestore Database → Create database**.
2. Choose **Production** mode (this project's rules already block unauthorized
   access).
3. Choose the region closest to your users. **The region cannot be changed
   later.** For users in Brazil, `southamerica-east1` is usually a good choice.
4. There is no need to create collections or indexes manually. The
   `hotwheels_items` collection is created on the first registration.

### 3.4 Publish the security rules

#### Option A — Firebase CLI (recommended)

Requirements: Node.js 18+ and a Google account with access to the project.

```bash
cd appphp
npx firebase-tools@latest login
npx firebase-tools@latest use YOUR_PROJECT_ID
npx firebase-tools@latest deploy --only firestore:rules,firestore:indexes
```

This folder's `firebase.json` already points to `firestore.rules` and
`firestore.indexes.json`. The `use` command creates a local `.firebaserc` — do
not upload that file to the server.

If you prefer to install the CLI globally:

```bash
npm install -g firebase-tools
firebase login
firebase use YOUR_PROJECT_ID
firebase deploy --only firestore:rules,firestore:indexes
```

#### Option B — Firebase Console

1. Open **Firestore Database → Rules**.
2. Copy the entire contents of `firestore.rules`.
3. Paste it into the editor, replacing the existing rules, and click
   **Publish**.

The rules are what prevent one user from reading another user's cars. Publish
them **before** sharing the app URL.

### 3.5 Verify the configuration

1. Run `npm run configure` (section 6.1) to write the keys and test the
   `apiKey`.
2. Run `npm run check` and fix any reported errors.
3. Open the app locally (section 6).
4. Create a test account at `#/login → Create account`.
5. Register a car with a photo.
6. In the Console, check under **Firestore → hotwheels_items** that the document
   has `userId`, `name`, `description`, `imageBase64`, `createdAt` and
   `updatedAt`.
7. Sign out and sign in again to confirm session persistence.

## 4. Local preferences

Keys used in `localStorage` (defined in `js/preferences.js`):

| Key | Values | Default |
| --- | --- | --- |
| `wheels.themeMode` | `light`, `dark`, `system` | `system` |
| `wheels.palette` | `crimson`, `ocean`, `emerald`, `violet`, `amber` | `crimson` |
| `wheels.locale` | `en-CA`, `fr-CA`, `pt-BR` | browser language |

- The `system` theme follows `prefers-color-scheme` in real time.
- Palettes are applied through CSS variables on `<html data-palette="...">`.
- A small script in `<head>` applies the theme and palette **before the first
  paint**, avoiding the white “flash”.
- The initial language is detected from the browser; if it is not `en`, `fr` or
  `pt`, it uses `pt-BR`.
- Clearing site data in the browser restores the defaults.
- The Firebase Auth session is kept in `localStorage`/IndexedDB by the SDK
  itself (`browserLocalPersistence`).

### Languages

Dictionaries live in `lang/*.json` and are loaded via `fetch`. A missing key in
one language falls back to `en-CA` and finally to the key name.
Dates use `Intl.DateTimeFormat` with the active locale.

To add a language:

1. Create `lang/xx-YY.json` by copying the keys from `en-CA.json`.
2. Add the language to the `LOCALES` array in `js/i18n.js`.
3. Add the code to the `detectLocale()` function if you want it detected
   automatically.
4. The navbar and settings screen selectors will display it automatically.

> File names are case-sensitive on Linux servers.
> Keep exactly `en-CA.json`, `fr-CA.json` and `pt-BR.json`.

## 5. How images are handled

1. The user chooses **gallery** or **camera** (`accept="image/*"` and
   `capture="environment"`).
2. The file is validated: it must be an image and be at most **20 MB**.
3. The image is decoded with `createImageBitmap` (respecting EXIF orientation)
   and, if unavailable, with `Image` + `URL.createObjectURL`.
4. The crop modal opens:
   - drag to reposition (mouse, touch or pen);
   - zoom slider from 100% to 300%;
   - 90° rotation in both directions;
   - reset button.
5. Export draws a **500 × 500** canvas and tries JPEG qualities
   `0.82 → 0.72 → 0.62 → 0.50` until the Base64 fits within **900,000
   characters**.
6. The Base64 is saved in `imageBase64` **without** the
   `data:image/jpeg;base64,` prefix. When displaying, the prefix is added by
   `imageSrc()`.
7. The 900,000-character limit keeps the document below Firestore's 1 MiB
   limit, with room for name, description and timestamps.

Notes:

- Firestore is **not** the ideal place for large files, but it was the project
  requirement (no Firebase Storage). A 500×500 JPEG photo is usually between
  30 and 150 KB (`~40,000` to `~200,000` characters in Base64), well below the
  limit.
- Formats such as HEIC may not be decoded by every browser. If cropping fails,
  use JPEG, PNG or WebP.
- SVG is not used as an item image: everything is re-encoded to JPEG by Canvas,
  which also eliminates malicious scripts embedded in images.

### 5.1 Local packaging OCR (Tesseract.js)

The **Scan packaging** button, shown above the Name and Description fields in
`#/collection/new` and `#/collection/:id/edit`, runs local OCR in the browser:

- Tesseract.js 7 is loaded on demand from the jsDelivr CDN, only on the first
  scan;
- the worker processes the already-cropped Base64 image, without sending the
  photo to an OCR server;
- the layout is analyzed in stages: full card, bottom band (model name), rotated
  side band (collection name) and, if necessary, a region focused on the
  collection number;
- `extractCarName`, `extractCollectionNumber` and `extractDescription` clean the
  text, discard noise (MATTEL, HOT WHEELS, age ranges, codes, copyright notices)
  and suggest Name and Description;
- the description uses the format `Collection name · XX/YYY`, for example
  `HW THE '90S · 2/10`;
- the result is only a suggestion: the fields remain editable and persistence
  stays in the existing layer (Firebase/Firestore in this project).

Notes:

- the first scan downloads the Tesseract core and the `eng` model (a few MB);
  afterwards the browser reuses the cache;
- sharp photos, without glare and with the full card, improve accuracy;
- the image used is the 500×500 cropped version; for packaging with very small
  text, move the camera closer before cropping;
- the button is disabled while there is no photo or while scanning is in
  progress.

## 6. Local debugging

The app **must be served over HTTP**. Opening `index.html` by double-clicking
(`file://`) does not work because the browser blocks ES modules and `fetch` of
JSON due to CORS.

### 6.1 Project script (recommended)

The CLI in `tools/` runs on **Windows, macOS and Linux**, installs no
dependencies and requires only Node.js 18 or newer (<https://nodejs.org/>).

```bash
cd appphp

# Windows (cmd or PowerShell)
tools\wheels.cmd

# macOS / Linux (first time)
chmod +x tools/wheels.sh
./tools/wheels.sh

# Any system
node tools/wheels.mjs
```

The interactive menu offers:

1. local debugging with live reload;
2. full project verification;
3. guided Firebase configuration;
4. generation of the `build/` folder;
5. opening the `build/` folder;
6. help.

Direct commands:

```bash
npm run dev -- --port 3000   # server at http://localhost:3000
npm run check                # files, HTML, CSS, JS, translations and Firebase
npm run check:online         # also tests CDNs and the apiKey
npm run configure            # writes the keys to js/firebase-config.js
npm run build                # generates build/ ready for Hostinger
```

Without npm, use `node tools/wheels.mjs <command>`. The server listens on
`127.0.0.1` by default, injects live reload and sends `Cache-Control: no-store`.
It also blocks `tools/`, `build/`, `.wheels/` and the configuration files,
mimicking production.

To test on a phone:

```bash
npm run dev -- --host 0.0.0.0 --no-open
```

Open `http://YOUR_MACHINE_IP:8080` on the phone and authorize that address in
Firebase (section 6.5).

## 7. Web “build”

This application is **static**: there is no compilation step like
`flutter build web`. The “build” is file validation + packaging for upload.
The CLI from section 6.1 automates both steps.

### 7.1 Build in one command (recommended)

```bash
cd appphp
npm run build
# equivalent to:
node tools/wheels.mjs build
```

The command:

1. runs the same checks as `check`;
2. refuses the build if Firebase is incomplete (unless
   `--allow-placeholder`);
3. deletes and recreates `build/` from scratch;
4. copies only the runtime: `index.html`, `css/`, `js/`, `lang/`, `assets/`,
   `manifest.webmanifest`, `robots.txt` and `.htaccess`;
5. verifies that no development file entered the folder;
6. writes the manifest to `.wheels/last-build.json`;
7. shows the file count and size.

Expected output:

```text
[OK] Build concluded: 16 files, 188.8 KB.
Contents of build/:
- index.html
- manifest.webmanifest
- robots.txt
- .htaccess
- css
- js (8 files)
- lang (3 files)
- assets
```

Useful options:

```bash
npm run build -- --online          # tests CDNs and apiKey first
npm run build -- --open            # opens the build folder at the end
npm run build -- --skip-check      # emergency; not recommended
npm run build -- --allow-placeholder
```

The result is `appphp/build/`, ready for upload. Upload the **contents** of that
folder to `public_html/app` — do not upload the `build` folder itself.

### 7.2 Manual validation (alternative)

If you prefer not to use the CLI, the commands below are part of the same check.

With Node.js installed, inside `appphp`:

**PowerShell (Windows):**

```powershell
Get-ChildItem js -Filter *.js | ForEach-Object {
  Get-Content -Raw $_.FullName | node --input-type=module --check
  if ($LASTEXITCODE -ne 0) { throw "Syntax error in $($_.Name)" }
}
```

**Bash / macOS / Linux / Git Bash:**

```bash
for f in js/*.js; do
  node --input-type=module --check < "$f" || exit 1
done
```

**Validate the three dictionaries:**

```bash
node -e "const fs=require('fs');for(const f of ['en-CA','fr-CA','pt-BR']){JSON.parse(fs.readFileSync('lang/'+f+'.json','utf8'));console.log(f,'ok')}"
```

**Check that every used key exists in all three languages:**

```bash
node -e "const fs=require('fs');const d=Object.fromEntries(['en-CA','fr-CA','pt-BR'].map(l=>[l,JSON.parse(fs.readFileSync('lang/'+l+'.json','utf8'))]));const used=new Set();for(const f of ['index.html','js/app.js']){const s=fs.readFileSync(f,'utf8');for(const m of s.matchAll(/\bt\(\s*'([a-zA-Z0-9_]+)'/g))used.add(m[1])}for(const l in d){const miss=[...used].filter(k=>!(k in d[l]));console.log(l,miss.length?'missing: '+miss.join(', '):'ok')}"
```

### 7.5 Optional: minify

Minification is not required to work, but it reduces the download:

```bash
npx html-minifier-terser --collapse-whitespace --remove-comments \
  --minify-css true --minify-js true index.html -o index.min.html
```

If you use `index.min.html`, rename it to `index.html` **after testing**.
The same applies to CSS/JS. Avoid minifying `firebase-config.js` manually
before configuring the keys.

### 7.6 Optional: compiled Tailwind (production)

The project uses the **Tailwind Play CDN** as a requirement. It compiles classes
in the browser and shows a console warning that it is not recommended for
production. For a faster version:

1. Install the Tailwind CLI (`npm i -D tailwindcss`).
2. Create `tailwind.config.js` with `darkMode: 'class'`, `content` pointing to
   `index.html` and `js/**/*.js`, and the `brand` palette with the CSS variables.
3. Create `css/tailwind.src.css` with `@tailwind base; @tailwind components;
   @tailwind utilities;`.
4. Generate `css/tailwind.css` with `npx tailwindcss -i css/tailwind.src.css -o
   css/tailwind.css --minify`.
5. In `index.html`, remove the `<script src="https://cdn.tailwindcss.com">`, the
   `tailwind.config` block and replace it with
   `<link rel="stylesheet" href="css/tailwind.css">`, keeping
   `css/styles.css` after it.

The CDN was kept so the app works without a build, as requested. If you do not
do this step, you just need internet on the first load.

### 7.7 Versioning and cache

- `index.html`, `lang/*.json` and `firebase-config.js` are served with
  `no-cache` + revalidation by `.htaccess`.
- CSS, JS and SVG have a 1-hour cache with revalidation.
- After updating files, clear the Hostinger cache (section 8.7) and do a
  hard refresh (`Ctrl+Shift+R`).
- If you need to force a specific file to change, add `?v=2` to the references
  inside `index.html`.

## 8. Deploy to Hostinger (`public_html/app`)

The final goal:

```text
public_html/
└── app/
    ├── index.html
    ├── .htaccess
    ├── css/
    ├── js/
    ├── lang/
    └── assets/
```

The URL will be `https://yourdomain.com/app/`.

### 8.1 Before uploading

1. Confirm that the Firestore rules have been published (section 3.4).
2. Confirm that the domain is under **Authentication → Authorized domains**.
3. Run the checklist from section 7.3 locally.
4. Run `npm run build` (section 7.1) and have the **contents** of
   `appphp/build/` ready (section 7.4).

### 8.2 Create the folder in hPanel

1. Log in to the **hPanel**.
2. Go to **Websites → Manage → File Manager**.
3. Open `public_html`.
4. Create the `app` folder (lowercase, no spaces).
5. Enter `public_html/app`.

If you already have WordPress or another site at the root, that is fine: the app
stays isolated under `/app`.

### 8.3 Upload the files

**Through the File Manager:**

1. Inside `public_html/app`, click **Upload**.
2. Upload the **contents** of `appphp/build/`: `index.html`,
   `manifest.webmanifest`, `robots.txt`, `.htaccess`, `css/`, `js/`, `lang/`
   and `assets/`.
3. If you prefer, compress the contents of `build/` into a `.zip`, upload it and
   use **Extract**.
4. **Important:** `index.html` must be **directly** at
   `public_html/app/index.html`. Do not upload the `appphp` folder or the
   `build` folder itself; upload its **contents**.

**Via FTP/SFTP (FileZilla, for example):**

1. Under **hPanel → Files → FTP Accounts** (or **SSH Access**), copy host,
   username, password and port.
2. Connect and open `public_html/app`.
3. Enable **Server → Force showing hidden files** to see and upload
   `.htaccess`.
4. Upload the files and folders in the structure above.

### 8.4 `.htaccess` is a hidden file

`.htaccess` starts with a dot and may not appear:

- In Hostinger's File Manager, enable **Settings → Show hidden files**.
- In FileZilla, use **Server → Force showing hidden files**.
- In macOS Finder, use `Cmd+Shift+.`.
- In Windows Explorer, use **View → Hidden items**.

Without `.htaccess` the app **still works**, but loses compression, caching and
the security headers.

### 8.5 Permissions

- Folders: `755`.
- Files: `644`.
- Do not use `777`.

In the File Manager, right-click → **Permissions** to adjust. In general,
Hostinger already applies the correct values on upload.

### 8.6 HTTPS and domain

1. Under **hPanel → Security → SSL**, install/enable the free certificate for
   the domain (Let’s Encrypt).
2. Enable **Force HTTPS**.
3. Open `https://yourdomain.com/app/` (with a trailing slash).
4. If you use `www`, make sure it is also in Firebase's authorized domains and
   that it redirects to the main domain.

### 8.7 Hostinger cache

Hostinger uses LiteSpeed and may have page caching enabled:

1. Under **hPanel → Advanced → Cache Manager** (or **LiteSpeed Cache**), clear
   the cache after each deploy.
2. If you use Cloudflare, do **Purge Everything** in the Cloudflare panel.
3. In the browser, use `Ctrl+Shift+R` (Windows) or `Cmd+Shift+R` (macOS).

If hosting cache ignores the `.htaccess` headers, disable page caching for
`/app` or for the entire site.

### 8.8 Test in production

1. Open the URL and confirm that the login screen appears.
2. Create an account or sign in with an existing one.
3. Add, edit and delete an item.
4. Reload the page on a hash route, for example
   `https://yourdomain.com/app/#/settings`.
5. Check the browser Console: there should be no
   `auth/unauthorized-domain`, `permission-denied` or 404 for
   `lang/*.json`.

### 8.9 Update the app

1. Replace `index.html`, `css/`, `js/`, `lang/` and `assets/` with the new ones.
2. Keep `.htaccess` (unless it has changed).
3. Clear the Hostinger/Cloudflare cache.
4. Hard refresh and test login.

Never delete the entire `app` folder during an update; upload over it or rename
the old one to `app_backup` first.

### 8.10 Subdomain (optional)

If you prefer `https://app.yourdomain.com`:

1. Create the subdomain in hPanel pointing the **document root** to
   `public_html/app`.
2. Add `app.yourdomain.com` to Firebase's authorized domains.
3. Enable SSL for the subdomain.
4. The URL becomes `https://app.yourdomain.com/` (without `/app`).

## 10. Security and limits

- **Never** put a service account key (Admin SDK) inside `public_html`. The app
  uses only the client-side SDK.
- The Web `apiKey` is public; the **Security Rules** are the real barrier.
- The app does not use `innerHTML`/`x-html` with user data; all text is rendered
  with `x-text`, which escapes HTML.
- Images are re-encoded to JPEG by Canvas before saving.
- Use **HTTPS** in production.
- Keep Firebase Auth with email enumeration protection (current default) and
  monitor usage in the Console.
- Optional: enable **Firebase App Check** (reCAPTCHA v3) to reduce abuse.
  This requires adding the SDK and configuring the key in the Console; it is not
  included to keep the app lightweight.
- Limits enforced on the client and in the rules:
  - name ≤ 120;
  - description ≤ 2000;
  - Base64 image ≤ 900,000 characters;
  - source file ≤ 20 MB;
  - password ≥ 6 characters.

### Privacy

The app is private: `robots.txt` blocks indexing and `index.html` has
`<meta name="robots" content="noindex, nofollow">`. There is no analytics or
third-party cookies; only Firebase and the Tailwind/Alpine CDNs.

- **Code:** keep a copy of `appphp/` (zip or Git repository).

- **Photos:** they are inside the documents (`imageBase64`). When exporting

## 12. Known limitations

- There is no email verification, account deletion or social login (they were
  not part of the original scope).
- There is no multi-photo upload per car; the model has one image.
- Tailwind Play CDN compiles in the browser; for maximum performance, follow
  section 7.6.
- There is no service worker; the app does not work offline.
- OCR uses Tesseract.js via CDN: the first scan requires internet to download
  the core and the language model. Recognition is local and the photo is not
  sent to any OCR service.
- The version shown in Settings is static (`1.0.0`) and can be changed in
  `index.html`.
- Firestore has a 1 MiB per-document limit; that is why the image is limited to
  500×500 and 900,000 characters.

## 13. Migrate old data (optional)

The Flutter app used:

```text
cars/{carId}
  ownerId, name, description, imageBase64, createdAt, updatedAt
```

This version uses:

```text
hotwheels_items/{itemId}
  userId, name, description, imageBase64, createdAt, updatedAt
```

In other words, you need to copy `ownerId → userId` and change the collection.
The old images were already 500×500 JPEG, so they can be copied as they are.

### Option 1 — start from scratch (recommended)

Keep the old data only as a backup and register the cars again. It is the
simplest option and carries no risk of mixing accounts.

### Option 2 — script with Firebase Admin SDK

Run it **on your computer**, never in `public_html`:

```bash
mkdir migrate && cd migrate
npm init -y
npm install firebase-admin
```

Create `migrate.mjs`:

```js
import { readFileSync } from 'node:fs';
import { initializeApp, cert } from 'firebase-admin/app';
import { getFirestore } from 'firebase-admin/firestore';

const serviceAccount = JSON.parse(
  readFileSync('./service-account.json', 'utf8'),
);

initializeApp({ credential: cert(serviceAccount) });
const db = getFirestore();

const source = await db.collection('cars').get();
let migrated = 0;

for (const doc of source.docs) {
  const data = doc.data();

  await db.collection('hotwheels_items').doc(doc.id).set({
    userId: data.ownerId,
    name: data.name ?? '',
    description: data.description ?? '',
    imageBase64: data.imageBase64 ?? '',
    createdAt: data.createdAt ?? new Date(),
    updatedAt: data.updatedAt ?? new Date(),
  });

  migrated += 1;
  console.log(`Migrated: ${doc.id}`);
}

console.log(`Total: ${migrated}`);
```

Steps:

1. Generate a service account key under **Project settings → Service accounts →
   Generate new private key**.
2. Save it as `service-account.json` **outside** the web project.
3. Run `node migrate.mjs`.
4. Check in the Console that the documents appeared in `hotwheels_items` with
   the correct `userId`.
5. Delete the private key from disk after migrating.

The Admin SDK ignores Security Rules, which is why the script can write on
behalf of users. Do not expose that key or that script on the web.

### Option 3 — Firestore export/import

Firestore export/import keeps the **collection names**, so it does not perform
the `cars → hotwheels_items` mapping by itself. Use the Admin SDK script for
that transformation. You can export beforehand as a backup:

```bash
gcloud firestore export gs://YOUR_BUCKET/backup-cars
```

## 14. Remove Flutter from the project (optional)

The Flutter code was **kept** in this delivery to allow rollback. The new app is
independent and can be published with only the `appphp/` folder.

Once everything is validated and you no longer need the old app:

1. **Make a full backup** of the project (zip or Git branch/tag).
2. Keep `app_config.env` in a safe place if you still need the credentials
   (it is ignored by Git and contains keys).
3. Remove, at the root:
   - `lib/`, `test/`, `android/`, `ios/`, `web/`, `tool/`, `build/`,
     `.dart_tool/`;
   - `pubspec.yaml`, `pubspec.lock`, `analysis_options.yaml`, `l10n.yaml`,
     `.metadata`, `.flutter-plugins-dependencies`, `wheelscollection.iml`;
   - `app_config.env`, `.env.example`;
   - `firebase.json`, `firestore.rules`, `firestore.indexes.json` from the root
     (the new versions are in `appphp/`);
   - the old `README.md` (replace it with one that points to `appphp/`).
4. Keep `appphp/` and, if desired, `docs/` and `.vscode/`.
5. Confirm that the Hostinger deploy uses only the contents of `appphp/`.

Example removal in PowerShell (**review before running** and run from the
project root):

```powershell
Remove-Item -Recurse -Force lib, test, android, ios, web, tool, build, .dart_tool

$oldFiles = @(
  'pubspec.yaml', 'pubspec.lock', 'analysis_options.yaml', 'l10n.yaml',
  '.metadata', '.flutter-plugins-dependencies', 'wheelscollection.iml',
  'app_config.env', '.env.example', 'firebase.json', 'firestore.rules',
  'firestore.indexes.json'
)
Remove-Item -Force $oldFiles
```

> Do not remove `appphp/`. If in doubt, move the old files to a
> `_flutter_backup/` folder instead of deleting them.
